## Context

**Current state** (`Mobile/src/screens/CalendarScreen.tsx`, verified in code):
- `fetchEvents()` calls `api.get('/api/sport-events/${teamId}', { params: { pageNumber: 1, pageSize: 50, descending: false } })` in parallel with `fetchSportEventTypeMap()` (`Mobile/src/api/sportEventTypes.ts`, calls `GET /api/sport-event-types`, returns `Record<number, string>`). Both are re-run whenever `teamId` changes (`useEffect(() => { fetchEvents(); }, [teamId])`).
- `events` (raw `SportEvent[]`, `Mobile/src/screens/components/EventCard.tsx`) and `eventTypeMap` are plain `useState`. The screen renders loading / error / empty / list states; empty state already exists (`empty-message` testID, text `'No hay eventos programados'`) and is reused as-is when filters match nothing.
- `EventCard` receives `eventTypeName={eventTypeMap[item.eventTypeId ?? -1]}` — so filtering by type is naturally expressed as "keep events whose `eventTypeId` is in the selected set" against the same map already in state.
- Backend `GetSportEvents.cs` (`Back/ExtractionApi/src/RFFM.Api/Features/Coaches/SportEvents/Queries/GetSportEvents.cs`): `SportEventsQuery` has `DateTime? StartDate`, `DateTime? EndDate`; handler does `query.Where(e => e.EveDateTime >= startUtc)` / `<= endUtc` when present, alongside the existing `TeamId` filter and `IRequireTeamMembership` gate. **Confirmed no backend change needed** — passing `startDate`/`endDate` as ISO strings in the existing `api.get` call's `params` is enough (axios/query-string serializes `Date` via `.toISOString()`; the endpoint parameter binds as `DateTime?`).
- No `eventTypeId` query param exists on the endpoint and none is being requested — type filtering **must** stay client-side, matching the acceptance criteria already agreed with the user.
- Persistence: the only storage mechanism installed in `Mobile/` today is `expo-secure-store` (`Mobile/src/auth/secureStore.ts`, wraps `setItemAsync`/`getItemAsync`/`deleteItemAsync`, used for the auth JWT in `AuthContext.tsx`). There is **no `AsyncStorage`** dependency in `Mobile/package.json`. No other screen persists a user preference today (team selection is route-param-driven, not stored).
- Testing stack (`Mobile/package.json`): Jest 29 + `jest-expo` preset + `@testing-library/react-native@^14.0.1`, tests co-located under `__tests__/`, `jest.mock('expo-secure-store')` already used in `CalendarScreen.test.tsx` (harmless no-op today since the screen doesn't touch it yet — will become load-bearing once this change lands).
- UI precedent: `Mobile/src/navigation/UserAvatarMenu.tsx` establishes the only existing "overlay" pattern in the app — RN core `Modal` (`transparent`, `visible`, `onRequestClose`) + a full-screen `Pressable` backdrop for outside-tap-to-close, RN core `Animated` for open/close transitions, no external UI/animation library. No file uses a date-picker library yet, and no icon is used as a direct dependency yet either (see that change's Decision 5 on promoting `@expo/vector-icons` to direct).

## Goals / Non-Goals

**Goals:**
- One user-facing entry point (a filter button in `CalendarScreen`'s header row) opening a filter panel with: event type (single-select, "Todos" = no filter, options from `eventTypeMap`) and date range (start date, end date, both optional/independent).
- Applying filters re-fetches from the backend with `startDate`/`endDate` and re-derives the rendered list by filtering the response client-side on `eventTypeId`.
- Filters persist across app restarts and screen re-navigation, scoped to the device/user (not the team), via `expo-secure-store` under a new dedicated key — reusing the only storage mechanism already in the project rather than introducing `AsyncStorage` as a second one.
- Filters auto-load on `CalendarScreen` mount (before or alongside the first fetch) and are used for that first fetch — the user should not see an unfiltered flash-then-filtered list when they had filters saved from last session (design must sequence "load persisted filters" before firing the initial `fetchEvents()`, or fold the fetch trigger into filter-load completion).
- Explicit "clear filters" control resets both fields and re-fetches.
- Switching `teamId` re-fetches using the *same* saved filters (they are global, not reset) — matches the existing `useEffect(() => { fetchEvents() }, [teamId])` dependency, now additionally depending on filter state so a filter change also re-fetches without needing a team change.
- Full TDD coverage: persistence module, filter panel component, and `CalendarScreen` integration (fetch params reflect saved/changed filters, empty-state on zero matches, clear resets and re-fetches).

**Non-Goals:**
- No new backend endpoint or query param — `eventTypeId` filtering never reaches the network.
- No multi-select event type filter (single "type or all" selection is what was agreed; extending to multi-select is a future enhancement if requested).
- No per-team filter scoping — explicitly global to the user per the agreed acceptance criteria.
- No change to pagination (`pageNumber`/`pageSize` stay as today); filters only add `startDate`/`endDate` to the same call.
- No i18n keys — `CalendarScreen.tsx` today uses hardcoded Spanish strings directly (`'Eventos'`, `'No hay eventos programados'`, etc.), not the `t()` helper from `Mobile/src/i18n`. New UI text follows the same hardcoded-Spanish convention for consistency with the rest of the screen (i18n keys exist only under the `attendance` namespace today; introducing filter strings there would be a scope creep on the i18n system itself).

## Decisions

1. **New component `Mobile/src/screens/components/EventFiltersModal.tsx`** (+ co-located `Mobile/src/screens/components/__tests__/EventFiltersModal.test.tsx`), mirroring `UserAvatarMenu.tsx`'s shape: self-contained overlay using RN core `Modal` + backdrop `Pressable` for outside-tap-to-close, but **controlled** (receives `visible`, `value`, `eventTypeOptions`, `onApply`, `onClear`, `onClose` as props) rather than owning its own open/closed state — `CalendarScreen` owns whether the modal is open (a `useState<boolean>` toggled by the new filter button) since it also needs to know the *current applied* filter values to build the fetch params. This matches the general RN pattern of "container screen owns state, presentational modal owns only its own draft-editing state before Apply is pressed."
   - *Alternative considered*: fully self-contained modal like `UserAvatarMenu` (owns open state, calls a persistence hook directly). Rejected — `CalendarScreen` needs the *applied* filter values to build `fetchEvents()`'s params and to filter `events` client-side by type, so the source of truth for "applied filters" has to live in (or be readable by) the screen either way; keeping the modal a controlled/presentational component avoids two copies of that state going out of sync.
2. **New persistence module `Mobile/src/screens/hooks/useEventFilters.ts`** (+ co-located test), a small custom hook wrapping `expo-secure-store` reads/writes, following the exact shape of `Mobile/src/auth/secureStore.ts` (`getItemAsync`/`setItemAsync`/`deleteItemAsync` under one dedicated key, wrapped in try/catch returning a safe default on failure — same defensive pattern `secureStore.ts` uses for `getToken()`). Storage key: `event_filters` (mirrors `secureStore.ts`'s `TOKEN_KEY = 'auth_token'` naming style), value JSON-stringified: `{ eventTypeId: number | null; startDate: string | null; endDate: string | null }` (dates stored as ISO strings, `null` meaning "not set").
   - *Alternative considered*: add `@react-native-async-storage/async-storage`. Rejected — it would be a **second** persistence mechanism alongside `expo-secure-store` for data that isn't actually sensitive, but introducing a new library for what is a small JSON blob is unwarranted when the project already has one working, tested storage wrapper; reusing `expo-secure-store` keeps the persistence surface area to one library, one pattern, one place to reason about failure modes. (Flagged as a decision worth confirming with the user — `expo-secure-store` is semantically meant for secrets, not preferences, but it is the only storage already in the dependency tree and this data (a small enum + two dates) carries no confidentiality requirement, so reuse over addition was chosen for consistency.)
   - The hook exposes `{ filters, isLoaded, saveFilters, clearFilters }`; `isLoaded` lets `CalendarScreen` defer its first `fetchEvents()` call until the persisted value (or its absence) is known, avoiding the unfiltered-flash problem from the Goals section.
3. **Date picker: add `@react-native-community/datetimepicker` via `npx expo install @react-native-community/datetimepicker`.** Confirmed (Expo docs v57, `/versions/v57.0.0/sdk/date-time-picker/`) that this package is "Included in Expo Go" — no dev-build/prebuild/EAS step required, consistent with how this Mobile app is currently run. It is the standard Expo-recommended date-selection UI (native iOS/Android system picker), used for both the start-date and end-date fields inside `EventFiltersModal`.
   - *Alternative considered*: plain text inputs for dates (no new dependency). Rejected — free-text date entry is error-prone and inconsistent with how RN apps conventionally expose date selection; since the package is confirmed Expo-Go-compatible with no build-pipeline impact, the UX gain outweighs the one new dependency. **This is a decision to flag explicitly to the user** — it is the one new npm dependency this change introduces.
4. **Event type filter UI: a horizontal row of selectable chips (or a simple RN `Pressable` list) built from `Object.entries(eventTypeMap)`, plus one "Todos" option representing "no type filter" (`eventTypeId: null`).** No new picker/dropdown library — reuses plain `Pressable`/`View`/`StyleSheet` exactly like `EventCard.tsx`'s existing chip style (`typeChip` style already in that file) for visual consistency, just made tappable/selectable in the new component.
5. **Wiring into `CalendarScreen.tsx`**:
   - Add `const { filters, isLoaded, saveFilters, clearFilters } = useEventFilters();`.
   - Change the fetch effect to depend on `[teamId, filters.startDate, filters.endDate, isLoaded]` and to no-op until `isLoaded` is true, so the persisted filters (or their absence) are always applied to the very first request.
   - Add `startDate: filters.startDate ?? undefined, endDate: filters.endDate ?? undefined` to the existing `params` object passed to `api.get`.
   - Derive the rendered list as `const visibleEvents = filters.eventTypeId == null ? events : events.filter(e => e.eventTypeId === filters.eventTypeId)` — computed at render time (not stored in state), so no new `useEffect`/state-sync bug surface.
   - Empty state: change the existing `events.length === 0` check to `visibleEvents.length === 0`, reusing the same `empty-message` testID/text — satisfies "no error, clear empty state" for the case where the date range comes back with events but all are filtered out by type, or where the date range itself returns nothing.
   - Add a filter-button `Pressable` (`testID="open-filters-button"`) in the header row next to `'Eventos'`, opening `EventFiltersModal`; a small badge/indicator (e.g. dot or filled icon state) when any filter is active is a nice-to-have, not required by the agreed acceptance criteria — left as an explicit follow-up if requested, not built now.
6. **`testID` conventions** (extending the existing kebab-case convention: `loading-indicator`, `error-message`, `retry-button`, `empty-message`, `event-item-{id}`):
   - `open-filters-button` (header button that opens the modal)
   - `event-filters-modal` (the modal root, only in the tree while `visible`)
   - `filter-type-option-{eventTypeId}` / `filter-type-option-all` (chip options)
   - `filter-start-date-input` / `filter-end-date-input` (date picker triggers)
   - `apply-filters-button`, `clear-filters-button`

## Risks / Trade-offs

- **[Trade-off] Reusing `expo-secure-store` for non-secret preference data** (Decision 2) is a slight semantic mismatch (it's designed for secrets/tokens) but avoids a second storage dependency for a one-screen feature; flagged above for the user to confirm or override before implementation.
- **[Risk] Sequencing persisted-filter-load before first fetch** (Goals + Decision 5) adds one more state variable (`isLoaded`) and effect dependency to `CalendarScreen`; if not done carefully this could cause a double-fetch on mount (once with defaults, once with loaded filters). `tasks.md` calls this out explicitly as something the RED tests must cover (assert `api.get` is called exactly once on initial mount with the *persisted* filters, not twice).
- **[Trade-off] New dependency `@react-native-community/datetimepicker`** — the one new native module this change adds. Confirmed Expo-Go-compatible (no prebuild), but still a real diff to `Mobile/package.json`/lockfile and a first-of-its-kind native UI dependency in this app; flagged per `Mobile/AGENTS.md`'s standing instruction to check versioned Expo docs before writing Expo-adjacent code (done above) and to be confirmed with the user before implementation starts.
- **[Risk] Client-side type filter combined with server-side pagination** (`pageSize: 50`): if a team has more than 50 events and the desired type is sparse among them, the filtered list could look incomplete (events of that type beyond the first 50 wouldn't be fetched). This already exists today for the unfiltered list (no infinite-scroll/pagination UI exists yet) and is **not** being fixed by this change — out of scope, but noted here so it isn't mistaken for a bug introduced by filtering.

## Migration Plan

- Mobile only, additive: one new npm dependency (`@react-native-community/datetimepicker`), two new files (modal component + persistence hook) plus their tests, and edits to `CalendarScreen.tsx`. No data/schema/backend changes, no migration needed. Existing users simply see no saved filters on first run after the update (`useEventFilters` returns `{ eventTypeId: null, startDate: null, endDate: null }` when the secure-store key is absent), i.e. behavior is identical to today until the user sets a filter for the first time.

## Post-implementation additions

Added after the initial TDD pass, at the user's request, since the date-range fields can produce an invalid combination (end before start) with no server round-trip to catch it, and filter persistence can fail silently:

7. **Inline date-range validation in `EventFiltersModal`**: a `getDateRangeError(draft)` helper flags `endDate < startDate` (when both are set) and renders an inline message (`testID="date-range-error"`, text "La fecha fin no puede ser anterior a la fecha de inicio") next to the date fields, recomputed live as either date changes. `apply-filters-button` is disabled (visually via reduced opacity and functionally via the `disabled` prop plus a guard in `handleApply`) while the error is present. This is a form-validation error, so it stays inline and blocking rather than using a toast — the user needs it to persist until they fix the input, not disappear after a few seconds.
8. **Reusable toast infrastructure** for non-blocking, transient errors: `Mobile/src/shared/components/Toast.tsx` (presentational, `error`/`success`/`info` variants, `coachColors` tokens) + `Mobile/src/shared/context/ToastContext.tsx` (`ToastProvider` + `useToast()`, auto-hides after 3s). Mounted once at the root in `Mobile/App.tsx` (inside `SafeAreaProvider`, wrapping `AuthProvider`) so any screen can call `useToast().showToast(...)`.
   - **Where it's used here**: `useEventFilters`'s `saveFilters`/`clearFilters` now return `Promise<boolean>` (persisted vs. not) instead of silently swallowing `SecureStore` failures. `CalendarScreen`'s `handleApplyFilters`/`handleClearFilters` call `showToast(...)` only when persistence fails — the filter still applies in memory for the current session (non-blocking), and the toast explains it won't survive an app restart.
   - **Where it's deliberately NOT used**: the events-endpoint failure path keeps the existing full-screen `error-message` + `retry-button` (already a tested, working "API error" pattern) — adding a toast on top would double-notify and doesn't fit a case where the whole list failed to load rather than one secondary action.
   - Scoped to this feature's files (`useEventFilters`, `CalendarScreen`) plus the reusable infra; not wired into other screens (`LoginScreen`, `TeamSwitcherScreen`) in this change — left as a follow-up if the team wants it as a consistent house style, since the user could not verify the toast visually in this session and asked to defer that review.
