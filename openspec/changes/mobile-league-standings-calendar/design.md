## Context

**Current state (confirmed in code, not assumed):**
- `Features/Federation/Competitions/Queries/GetClassification.cs` (`GET /classification`) and `.../GetCalendar/GetCalendar.cs` (`GET /calendar`) already scrape/return RFFM data via `ICompetitionService.GetClassification(groupId, ct)` and `ICalendarService.GetCalendarAsync(competitionId, groupId, ct)`. Both take `season`/`competition`/`group`/`playType` query params with hardcoded defaults (`season=21, competition=25255269, group=25255283, playType=1`); `season` and `playType` are accepted but **not actually used** by either handler today — only `competition`/`groupId` drive the call. Both service methods take `int` parameters (`groupId`, `competicion`).
- `Features/Federation/Competitions/Queries/GetCompetitions.cs` (`GET /competitions`, unauthenticated) and `GetGroups.cs` (`GET /groups?competitionId=`) already expose RFFM's own **scraped** competition/group catalog via `ICompetitionService.GetCompetitionsAsync`/`GetGroupsAsync`, returning `ResponseCompetition(int Id, string Name, string CategoryGroup)` / `ResponseGroup(int Id, string Name)`. These `Id` values are RFFM's real competition/group ids — the same ids `ICompetitionService.GetClassification`/`ICalendarService.GetCalendarAsync` expect as input. This is the correct source of truth for resolving a team's RFFM competition/group; it is a **completely separate ID space** from the local `Leagues` catalog table (see "Corrected resolution model" below).
- `Domain/Aggregates/UserClubs/Team.cs` already carries `LeagueId` (`int?`, private setter) and `LeagueGroup` (`int?`, private setter). `Team.LeagueId` is a **real FK** to the local `Leagues` table (`Domain/Entities/Competitions/League.cs`, `DbSet<League> AppDbContext.Leagues`), enforced by Postgres (`FK_Teams_Leagues_LeagueId`) and by EF (`TeamEntityConfiguration.cs`). `League` is scoped by `CategoryId` and is **only ever read**, never written (`Features/Coaches/Competitions/Leagues/Queries/GetLeagues.cs`, `GET /api/catalog/leagues/{categoryId}` — no `CreateLeague`/seed/sync command exists anywhere). It is used today by the Front Coach app's `LeagueSelect` component to categorize a team within the app's own local taxonomy (e.g. "Liga Alevín 1ª Provincial"). **This field and its Front usage are out of scope for this change and are not modified.**
- `Team.LeagueGroup` is a **plain `int?`** with no FK, no catalog entity, and no validation anywhere in the codebase — also out of scope and not modified.

## Corrected resolution model (supersedes the earlier draft)

**Problem identified in the earlier draft**: it proposed resolving Mobile's classification/calendar/next-match from `Team.LeagueId`/`Team.LeagueGroup`, passing them straight through as if they were RFFM's own competition/group ids. Because `Team.LeagueId` is a real FK into the local `Leagues` table (50 seeded rows, ids 1–50) and nothing in the codebase seeds `Leagues` from RFFM's scraped competitions, there is no guarantee — and in practice no reason to expect — that `League.Id` values coincide with real RFFM competition ids. Using them directly would silently return wrong or empty scrape results.

**Fix adopted**: introduce two new, purpose-built fields on `Team` that store RFFM's own ids directly, decoupled from the local `Leagues` catalog:

- `Team.RffmCompetitionId` (`int?`) — RFFM's own competition id, same id space as `GetCompetitions.ResponseCompetition.Id` and the `competition`/`competicion` parameter already consumed by `ICompetitionService`/`ICalendarService`.
- `Team.RffmGroupId` (`int?`) — RFFM's own group id, same id space as `GetGroups.ResponseGroup.Id` and the `group`/`groupId` parameter already consumed by `ICompetitionService`/`ICalendarService`.

Both are plain nullable `int` columns, **no FK** — RFFM's competition/group catalog is external (scraped), not a local table, so there is nothing to reference. This mirrors how `Team.LeagueGroup` is already a plain unvalidated `int?` today (same shape, no catalog).

`Team.LeagueId`/`Team.LeagueGroup` (the local `Leagues` catalog FK) are **completely untouched**: different fields, different feature, different Front selector (`LeagueSelect`, unchanged). The two features happen to share the word "liga/league" in casual usage but are now structurally independent — no shared field, no shared endpoint, no shared Front component.

**Resolution model**: `{teamId}` in the new Mobile routes is used both for the `IRequireTeamMembership` permission check (proving the caller belongs to that team) **and** for resolving which RFFM competition/group to query — the handler loads `Team` by id (via `AppDbContext`, `AsNoTracking()`), reads `RffmCompetitionId`/`RffmGroupId` directly off that entity. This is per-team, not per-user: two members of the same team always see the same competition data, and a user belonging to multiple teams gets each team's own data. `FederationSetting`/`IFederationSettingService` (a per-user Federation-SPA concept) is still explicitly **not used** — no change from the earlier draft on this point.

## Goals / Non-Goals

**Goals:**
- Expose classification, full calendar, and next-match for the requested `{teamId}`'s own RFFM competition/group via three new Mobile-shaped, permission-gated endpoints.
- Reuse `ICompetitionService`/`ICalendarService` as-is — zero changes to Federation scraping/services or their existing routes, and zero dependency on `FederationSetting`/`IFederationSettingService`.
- Return a defined, non-throwing response when the team's `RffmCompetitionId`/`RffmGroupId` are `null` (not yet associated with a competition) — `200 OK` with an explicit empty/"not associated" result, not `500`.
- Give Coaches a way to set/update a team's RFFM competition (`RffmCompetitionId`) and group (`RffmGroupId`) **after** creation, closing the gap where `UpdateTeam.cs` never touches these fields — the prerequisite for the three read endpoints above to ever resolve real data for teams not already associated at creation time.
- Keep the local `Leagues` catalog (`Team.LeagueId`/`LeagueGroup`, `GetLeagues.cs`, `LeagueSelect`) fully isolated from this change — no shared code path, no shared field.

**Non-Goals:**
- No new `season`/`playType` per-team configurability — both stay hardcoded at their current Federation-endpoint defaults, matching existing behavior.
- No change to how `{teamId}` route membership is checked — reused as-is from `IRequireTeamMembership`.
- No caching of the new Mobile endpoints in this change (verify during implementation whether `CompetitionService`/`CalendarService` already cache internally; do not add a second caching layer at the Mobile query level unless a real perf issue is found).
- No Mobile (Expo/React Native) client work — that is a separate, coordinated change.
- No Front SPA (Coach app) UI implementation — that is a separate, coordinated change with `front-specialist`; this design only specifies the backend contract it will call and the shape of the selector it implies (see below).
- No change whatsoever to `Team.LeagueId`/`LeagueGroup`, `League.cs`, `GetLeagues.cs`, or `LeagueSelect` — that local catalog feature is untouched.
- No reconciliation/backfill of existing teams' `RffmCompetitionId`/`RffmGroupId` — they start `null` for all existing rows after the migration; Coaches associate them going forward via the new command.

## Decisions

1. **One feature file per query**, vertical-slice style, under `Features/Mobile/Competitions/Queries/`: `GetTeamClassification.cs`, `GetTeamCalendar.cs`, `GetTeamNextMatch.cs`. Each is a full slice (route + `IQueryApp<T>` record + handler + DTOs) per repo convention, matching the one-query-per-file pattern used by `GetPlayerSeasonCards.cs`/`GetEventAttendanceRoster.cs`.
   - *Alternative considered*: one file exposing all three routes (mirrors `FederationGetClassification`/`FederationGetCalendar` being source-grouped). Rejected — Mobile's existing precedent is strictly one query per file; consistency with the nearest sibling wins.

2. **Resolution reads `Team.RffmCompetitionId`/`Team.RffmGroupId` directly, no separate lookup service**: all three handlers fetch the `Team` by `{teamId}` (`AppDbContext.Teams.AsNoTracking().SingleOrDefaultAsync(t => t.Id == teamId, ct)`) and read `RffmCompetitionId`/`RffmGroupId` off it. If either is `null`, return an explicit **empty** result DTO (`Teams = []`, `MatchDays = []`, `NextMatch = null`) with `200 OK` — not a `404`/`ProblemDetails`. Rationale: "team not yet associated with a competition" is an expected, common state, not an error condition. No shared `FeatureService` is introduced for this single-entity read — three call sites of one simple `Team` lookup is not enough duplication to justify one.
   - *Alternative considered*: `404 Not Found` / `ProblemDetails` when `RffmCompetitionId`/`RffmGroupId` are null. Rejected — `ProblemDetails` should represent real errors; "not yet associated" is normal, expected UI state for a subset of teams.
   - *Alternative considered (rejected)*: resolving via `Team.LeagueId`/`LeagueGroup` (the local catalog). Rejected — see "Corrected resolution model" above; wrong id space.
   - *Alternative considered (rejected in an earlier draft)*: resolving via the calling user's primary `FederationSetting`. Rejected by the user — `FederationSetting` is a Federation-SPA, per-user concept and must not be reused by Mobile.

3. **`GetTeamNextMatch` is a thin derivation over the same calendar data**, not a new scrape: internally does the same `Team` resolution + `ICalendarService.GetCalendarAsync`, then selects the earliest `MatchResponse` across all `MatchDays` where the match's date is `>= DateTime.UtcNow.Date` AND the match is not yet finished (exact "unplayed" predicate to be confirmed against real `CalendarService` scrape output during implementation). Returns `null`/empty DTO if no future match exists (end of season) or if the team has no `RffmCompetitionId`/`RffmGroupId`.
   - *Alternative considered*: a dedicated RFFM scrape/endpoint for "next match". Not found in `ICompetitionService`/`ICalendarService` — deriving from `/calendar` is the only available data source.

4. **New `CoachFeatureRoutes` constant**: `CompetitionData = "/mobile/competition-data"`, shared by all three queries (Read-only), seeded in `WebApplicationExtensions.cs` for `Player`, `FamilyMember`, `Coach` (permission value `1` = Read, mirroring `PlayerSeasonCards`'s seeding block). Administrator bypasses as usual.
   - *Alternative considered*: three separate `FeatureRoute`s (one per query). Rejected — all three represent the same "can this role see competition data" concern.

5. **DTOs are new, Mobile-specific records** (`MobileClassificationRowDto`, `MobileCalendarMatchDayDto`, `MobileMatchDto`, `MobileNextMatchDto`), mapped from the existing `TeamResponse`/`CalendarMatchDayResponse`/`MatchResponse`. Only the fields Mobile actually needs are projected. Numeric-looking fields that are `string` in `TeamResponse` (RFFM scrape quirk) are parsed to `int` in the Mobile DTO with a safe fallback (`0`) if parsing fails.

6. **New `Team` fields, no FK**: `Team.RffmCompetitionId` (`int?`), `Team.RffmGroupId` (`int?`), added as plain nullable `int` columns via a new EF migration (see Migration Plan). No navigation property, no FK constraint — RFFM's competition/group catalog is external/scraped, there is no local table to reference. `Team.UpdateRffmCompetitionId(int? rffmCompetitionId)` / `Team.UpdateRffmGroupId(int? rffmGroupId)` are added to `Team.cs` as intent-revealing update methods, mirroring the existing `UpdateLeagueId`/`UpdateLeagueGroup` pattern (kept for the local catalog, untouched). `CreateTeamCommand`/`TeamModel` gain matching optional `RffmCompetitionId`/`RffmGroupId` properties so a team can optionally be associated at creation time too, same as `LeagueId`/`LeagueGroup` are today.
   - *Alternative considered*: reuse `LeagueId`/`LeagueGroup` for both purposes. Rejected — this is exactly the bug being corrected; the two id spaces (local `Leagues` catalog vs. RFFM's own scraped catalog) are unrelated and must not be conflated in a single pair of fields.

7. **New command `UpdateTeamCompetition` — one file, vertical slice — under `Features/Coaches/Teams/Commands/UpdateTeamCompetition.cs`** (renamed from the earlier draft's `UpdateTeamLeague.cs` — that name is now reserved terminology for the untouched local Liga catalog and would be misleading here). Rationale for a dedicated file: `UpdateTeam.cs` already has a narrow, single-purpose shape (Name/UrlPhoto/CategoryId/ClubId only), mirroring the repo's existing pattern of splitting team mutations into dedicated single-purpose commands (`UploadTeamPhoto.cs`, `AddPlayerTeam.cs` are already separate from `UpdateTeam.cs` for the same reason). Associating an RFFM competition/group is a distinct, occasional operation and deserves its own permission-checked, cache-invalidating slice.
   - Route: `PUT api/catalog/team/{id}/competition` — mirrors `UpdateTeam.cs`'s `PUT api/catalog/team/{id}` shape with a suffix segment, true partial update of an existing resource (PUT semantics).
   - Request body (JSON): `UpdateTeamCompetitionCommand { string Id (bound from route), int? RffmCompetitionId, int? RffmGroupId }`. Both fields nullable and independently settable — either can be explicitly `null` to *clear* an existing association. The command always sets both fields from the request (all-or-nothing, matching `UpdateTeamCommand`'s existing style), not sparse/PATCH semantics.
   - Response: `200 OK`, empty body (matches `UpdateTeam.cs`'s `Results.Ok()`); `404`-mapped `ProblemDetails` (via `KeyNotFoundException`, same convention as `UpdateTeamHandler`/`DeleteTeamHandler`) if `{id}` does not resolve to an existing `Team`.
   - Interfaces: `IRequest, IInvalidateCacheRequest, IRequireFeaturePermission` — same three as `UpdateTeamCommand`/`DeleteTeamCommand`. `PrefixCacheKey => TeamConstants.CachePrefix`, `FeatureRoute => CoachFeatureRoutes.ClubTeams` (reused, no new route constant), `RequiredPermission => "ReadWrite"`. No `IRequireTeamMembership` — that interface is exclusively used by `Features/Mobile/*` queries for Player/FamilyMember scoping; Coach-app team commands never use it.
   - Handler flow (mirrors `UpdateTeamHandler`): load `Team` by id via `AppDbContext.Teams.FirstOrDefaultAsync` (tracked, not `AsNoTracking`, since it mutates) → `KeyNotFoundException` if not found → `team.UpdateRffmCompetitionId(request.RffmCompetitionId); team.UpdateRffmGroupId(request.RffmGroupId); await _catalogDbContext.SaveChangesAsync(cancellationToken);`. **No FK/category-scoped existence check is needed here** (unlike the earlier draft's `LeagueId` check against the local `Leagues` table) because `RffmCompetitionId`/`RffmGroupId` are plain unvalidated ids from an external catalog, same as `LeagueGroup` already is today — there is no local row to validate against. Optionally, the handler MAY call `ICompetitionService.GetGroupsAsync(competitionId)` to soft-verify the pair is a real, currently-scraped RFFM combination before persisting; left as an implementation-time decision (see Open Questions), not required for this design to be complete, since `GetCompetitions`/`GetGroups` already give the Front SPA everything it needs to only ever submit valid pairs via the dropdown.
   - Validator (`FluentValidation`, format-only): `RuleFor(r => r.RffmCompetitionId).GreaterThan(0).When(r => r.RffmCompetitionId.HasValue)`; `RuleFor(r => r.RffmGroupId).GreaterThan(0).When(r => r.RffmGroupId.HasValue)`.
   - *Alternative considered*: extend `UpdateTeamCommand`/`UpdateTeamHandler` in place. Rejected — same reasoning as the earlier draft: keeps the existing "always send Name/CategoryId/ClubId/UrlPhoto together" contract clean for a Front form that only wants to change competition/group.

## Front SPA contract (Coach app) — specification only, implementation by `front-specialist`

The Coach app needs a **new, separate selector** — two chained dropdowns — distinct from the existing `LeagueSelect` (which stays wired to `GET /api/catalog/leagues/{categoryId}` / `Team.LeagueId`, untouched):

1. **Competition dropdown**: populated from `GET /competitions` (`Features/Federation/Competitions/Queries/GetCompetitions.cs`, unauthenticated today, no `FeatureRoute`) → `ResponseCompetition(int Id, string Name, string CategoryGroup)`. On selection, captures `Id` as the candidate `RffmCompetitionId`.
2. **Group dropdown**: populated from `GET /groups?competitionId={selectedCompetitionId}` (`Features/Federation/Competitions/Queries/GetGroups.cs`) → `ResponseGroup(int Id, string Name)`, re-fetched/re-enabled whenever the competition selection changes; disabled/empty until a competition is chosen. On selection, captures `Id` as the candidate `RffmGroupId`.
3. On submit, the form calls `PUT /api/catalog/team/{id}/competition` with `{ RffmCompetitionId, RffmGroupId }` (both `null` if the Coach explicitly clears the association via a "not associated" option).

This is a **new component**, not a variant of `LeagueSelect` — the two selectors have unrelated data sources (local catalog vs. RFFM scrape) and unrelated target fields (`LeagueId`/`LeagueGroup` vs. `RffmCompetitionId`/`RffmGroupId`). Suggested naming for the new component, left to `front-specialist`'s judgment at implementation time: `RffmCompetitionSelect` / `TeamCompetitionAssociationForm`, placed alongside `LeagueSelect` in the same Coach app `components/` directory it already lives in. No design decision is made here on exact component boundaries beyond "it must call `GET /competitions`, then `GET /groups?competitionId=`, then `PUT /api/catalog/team/{id}/competition`" — that's the backend contract this change guarantees.

## Risks / Trade-offs

- **[Risk] `Team.RffmCompetitionId`/`RffmGroupId` start `null` for every existing team after migration** → every team resolves to the empty/"not associated" state until a Coach explicitly associates it via the new command. Expected and explicitly handled (Decision 2); no backfill is attempted (Non-Goals).
- **[Risk] No server-side verification that a submitted `(RffmCompetitionId, RffmGroupId)` pair is a real, currently-valid RFFM combination** → the Front dropdown flow makes it structurally hard to submit an invalid pair (group list is always fetched scoped to the chosen competition), but the endpoint itself doesn't re-verify server-side by default (Decision 7). If a stale/direct API call sets an invalid pair, the Mobile endpoints simply resolve to empty scrape results (same graceful-empty behavior as "not associated") rather than an error — not a data-integrity risk, only a UX one. Flagged as an implementation-time judgment call (Open Questions).
- **[Risk] `season`/`playType` hardcoded defaults could drift once a new RFFM season starts** → same pre-existing risk as the Federation endpoints being reused; out of scope to fix here.
- **[Risk] `GetTeamNextMatch`'s "unplayed" predicate is unverified against live scrape data** → flagged as an implementation-time verification step; not blocking design approval.
- **[Risk] No caching at the Mobile layer** → verify during implementation whether `ICompetitionService`/`ICalendarService` already cache; add `EasyCaching`-based caching only if a real perf issue is found.

## Migration Plan

- **New EF Core migration required** (not generated yet, this design only names it): proposed name `AddRffmCompetitionAndGroupToTeam`, generated with:
  ```
  cd Back/ExtractionApi
  dotnet ef migrations add AddRffmCompetitionAndGroupToTeam --project src/RFFM.Api --startup-project src/RFFM.Host --context AppDbContext
  ```
  (exact `--project`/`--context` flags to be confirmed against `manage-migrations.ps1`'s actual invocation at implementation time). The migration adds two nullable `integer` columns to the `app.Teams` table: `RffmCompetitionId`, `RffmGroupId`. No FK, no index required unless query performance on these columns becomes a concern (not expected — always looked up by `Team.Id`, not by these columns).
- Otherwise additive only: three new query files, one new `CoachFeatureRoutes` constant, one new seeded `FeaturePermission` block, one new command file (`UpdateTeamCompetition.cs`) reusing the existing `ClubTeams` `FeatureRoute`/permission rows. No changes to existing Federation routes/services, `UpdateTeam.cs`/`CreateTeam.cs`'s existing fields, `Team.LeagueId`/`LeagueGroup`, or the `Leagues` table/FK. Safe to deploy independently of any Mobile or Front SPA client work.

## Open Questions

- Exact field(s) in the scraped `MatchResponse` that reliably indicate "not yet played" for the next-match filter (to be confirmed against a live/sample scrape during implementation — see Risks).
- Whether `UpdateTeamCompetition`'s handler should soft-verify the submitted `(RffmCompetitionId, RffmGroupId)` pair against `ICompetitionService.GetGroupsAsync` before persisting, or trust the Front dropdown flow to only ever submit valid pairs (see Decision 7 and Risks) — left to implementation-time judgment, does not block this design.
- Exact `dotnet ef migrations add` invocation flags (`--project`/`--startup-project`/`--context`) — confirm against `Back/ExtractionApi/manage-migrations.ps1` at implementation time rather than assuming the flags above are exact.
