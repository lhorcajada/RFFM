## Why

Mobile (Coach/Familia) needs to show league standings, the full matchday calendar with results, and the team's next fixture — the same RFFM data already shown in the Front Federation SPA. The backend already scrapes and exposes this data (`/classification`, `/calendar`, `/calendar/matchday`), but those routes are Federation-SPA-shaped (per-request `season`/`competition`/`group`/`playType` query params) and are not Mobile-friendly. Mobile has no way today to fetch this without duplicating that resolution logic client-side, and coupling Mobile directly to Federation's routes would make future SPA-driven changes to those contracts a breaking change for Mobile too.

**Correction to an earlier draft of this proposal**: the original design resolved a team's RFFM competition/group from `Team.LeagueId`/`Team.LeagueGroup`. Those fields are a **local catalog FK** (`Team.LeagueId` → `Leagues` table, 50 seeded rows, category-scoped, already used today by the Front Coach app's `LeagueSelect`/`GET /api/catalog/leagues/{categoryId}` to categorize teams) and have no established mapping to RFFM's own scraped competition/group ids — nothing in the codebase seeds `Leagues` from RFFM data. Reusing them for RFFM resolution would silently return wrong/empty results for any team whose local `League.Id` doesn't coincide with a real RFFM competition id. This revision replaces that resolution source with two new, purpose-built fields on `Team` that store RFFM's own ids directly, and leaves `LeagueId`/`LeagueGroup` (the local catalog) completely untouched — that remains a separate, existing feature.

## What Changes

- **Backend — new Mobile feature slice(s)** under `Back/ExtractionApi/src/RFFM.Api/Features/Mobile/Competitions/`, reusing `ICompetitionService` / `ICalendarService` (no scraping logic duplicated):
  - `GET /api/mobile/teams/{teamId}/classification` → league table for the team's competition/group.
  - `GET /api/mobile/teams/{teamId}/calendar` → full matchday-by-matchday calendar with results.
  - `GET /api/mobile/teams/{teamId}/next-match` → single next fixture, derived by filtering the calendar for the first unplayed match with `Date >= today` (mirrors the Front SPA's client-side derivation, moved server-side).
- **New `Team` fields** (`Back/ExtractionApi/src/RFFM.Api/Domain/Aggregates/UserClubs/Team.cs`): `RffmCompetitionId` (`int?`) and `RffmGroupId` (`int?`) — no FK, since these are external RFFM ids, not local catalog rows. These are the fields the three Mobile endpoints resolve from. `Team.LeagueId`/`Team.LeagueGroup` (the local `Leagues` catalog FK, used by the Coach app's category picker) are **not reused and not modified** — separate feature, separate concern, untouched by this change. `SeasonId` is unchanged and continues to scope which season's team record this is.
- **Team not yet associated with a competition**: if the resolved `Team.RffmCompetitionId` or `Team.RffmGroupId` is `null`, the three endpoints return an explicit "not associated" empty result (`200 OK`), not an error — see design.md.
- **Backend — new command to associate a team with its RFFM competition/group post-creation**: `RffmCompetitionId`/`RffmGroupId` are only ever set at team creation via `CreateTeamCommand` (`Features/Coaches/Teams/Commands/CreateTeam.cs`); `UpdateTeam.cs` never touches them, so a Coach has no way to associate (or correct) a team's RFFM competition after creation — most existing teams will permanently resolve to the "not associated" empty state for the three Mobile endpoints otherwise. This change adds `PUT /api/catalog/team/{id}/competition` (`Features/Coaches/Teams/Commands/UpdateTeamCompetition.cs`, renamed from the earlier draft's `UpdateTeamLeague.cs` — the earlier name conflated this with the local Liga catalog), a single-purpose vertical slice, following the same pattern as `UpdateTeam.cs`/`DeleteTeam.cs` (`IRequireFeaturePermission`, `RequiredPermission = "ReadWrite"`, `FeatureRoute = CoachFeatureRoutes.ClubTeams`, cache invalidation via `TeamConstants.CachePrefix`). The **Front SPA (Coach app)** UI that calls this endpoint is out of scope here — coordinated separately with `front-specialist`; see design.md for the new chained-dropdown selector this endpoint implies (distinct from the existing `LeagueSelect`).
- **Auth/authorization**: reuse the `{teamId}` route pattern + `IRequireFeaturePermission` (Read) + `IRequireTeamMembership`, matching `GetPlayerSeasonCards`/`GetEventAttendanceRoster`. No new roles or permission routes beyond one new `FeatureRoute` constant for this feature.
- **DTOs**: new Mobile-shaped response records (`MobileClassificationDto`, `MobileCalendarDto`, `MobileNextMatchDto`) — thin, camelCase-friendly projections of the existing `ClassificationResponse`/`CalendarResponse`/`MatchResponse`, not the raw Federation response types.

## Capabilities

### New Capabilities
- `mobile-competition-data`: Mobile Coach/Familia app can fetch a team's league classification, full calendar with results, and next match, resolved server-side from the team's own `RffmCompetitionId`/`RffmGroupId`.
- `coach-team-competition-association`: A Coach (or Administrator) can associate/re-associate an existing team's RFFM competition (`Team.RffmCompetitionId`) and group (`Team.RffmGroupId`) after creation, via a dedicated Coach-scoped command — the prerequisite that lets teams created without this data (or needing correction) become resolvable by the `mobile-competition-data` endpoints. (Renamed from the earlier draft's `coach-team-league-association` to avoid confusion with the pre-existing, untouched local Liga catalog feature.)

### Modified Capabilities
(none — no existing spec covers Mobile competition data; the underlying Federation classification/calendar behavior is unchanged, only reused; `UpdateTeam.cs` itself is not modified — the new command is additive and separate; the existing local Liga/Grupo catalog feature (`Team.LeagueId`/`LeagueGroup`, `GetLeagues.cs`, `LeagueSelect` in Front) is not modified either)

## Impact

- **Backend**: new files under `Features/Mobile/Competitions/` (Queries: `GetTeamClassification`, `GetTeamCalendar`, `GetTeamNextMatch`); one new `CoachFeatureRoutes` constant + seeded `FeaturePermission` rows (mirroring `GetPlayerSeasonCards`); new `Features/Coaches/Teams/Commands/UpdateTeamCompetition.cs` (command + validator, reusing the existing `ClubTeams` `FeatureRoute`); domain change to `Team.cs` (two new nullable `int` columns, no FK) + one new EF migration — see design.md for the proposed migration name; no changes to `Features/Federation/Competitions/*` or `Features/Federation/Settings/*`; no changes to `Team.LeagueId`/`LeagueGroup` or `Leagues`/`League.cs`.
- **Mobile** (out of scope for this backend proposal — to be coordinated separately): new screens/API calls consuming the three `mobile-competition-data` endpoints once available.
- **Front SPA — Coach app** (out of scope for this backend proposal — to be coordinated separately with `front-specialist`): a new chained-dropdown selector (competition → group) calling `PUT /api/catalog/team/{id}/competition`, consuming the existing `GET /competitions` and `GET /groups?competitionId=` endpoints — a different, additional selector from the existing `LeagueSelect`/`GET /api/catalog/leagues/{categoryId}`, which is unaffected by this change.
- **Open dependency**: if the requested team's `RffmCompetitionId`/`RffmGroupId` are `null` (team never associated with a competition at creation, and not yet associated via the new command), these endpoints have nothing to resolve against — design.md defines the explicit "not associated" empty response for that case.
